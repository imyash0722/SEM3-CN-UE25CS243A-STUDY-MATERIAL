Persistent HTTP (HTTP 1.1) UNIVERSITY

b) Persistent HTTP — without pipelining

With Persistent HTTP, the server keeps the TCP connection open after sending a response. Subsequent objects
can be sent over this existing connection. Because it is without pipelining, the client must wait for the
current response before issuing the next request.

With persistent HTTP: TCP connection is established only once - 1 RTT
1 RTT to establish the initial TCP connection

1 RTT to request and receive the base HTML file

6 RTT to request and receive the 6 images sequentially (1 RTT per image)
Total Time = 1 RTT (TCP) + 1 RTT (HTML) + 6 RTT (images) = 8 RTTs

Each of the 7 objects requires an HTTP request/response cycle > 7 RTTs
Therefore: 1RTT + 7RTT = 8RTT == 8x80 =640 ms

Answer: 640 ms =0.64 s

COMPUTER NETWORKS %% PES
Persistent HTTP (HTTP 1.1) UNIVERSITY

d) Persistent HTTP with pipelining

With Persistent HTTP with pipelining, the client opens a single TCP connection and can send multiple HTTP requests back-to-back without
waiting for each response.

After downloading the HTML:
1 RTT to establish the single TCP connection.
1 RTT to request and receive the base HTML file.

1 RTT to request and receive all 6 images. The client parses the HTML file, discovers all 6 images, and sends requests for all of them
together in a single batch.

With pipelining, it sends requests for all 6 images without waiting for individual responses.
Approximately 1 RTT is needed for the requests and responses to begin.
Total Time = 1 RTT (TCP) + 1 RTT (HTML) + 1 RTT (All 6 images) = 3 RTT
Since RTT = 80 ms: ==>3x80 =|240 ms

Transport Layer Security (TLS) Protocol

= widely deployed security protocol above the transport layer
* supported by almost all browsers, web servers: https (port 443)

= provides:
* confidentiality: via symmetric encryption (Encrypts data so eavesdroppers can't
read it.)
* integrity: via cryptographic hashing (Ensures data isn't altered or corrupted in
transit.)
* authentication: via public key cryptography (Verifies that the client is actually
talking to the genuine server, not an impostor.)

= history:
* early research, implementation: secure network programming, secure sockets
* secure socket layer (SSL) deprecated [2015]
* TLS 1.3: RFC 8846 [2018]

Transport Layer Security (TLS) Protocol DA RReerv

* SSL (Secure Sockets Layer): Created by Netscape in the mid-1990s.

* SSL 1.0: Never released publicly due to major flaws.

* SSL 2.0 & 3.0: Released in 1995 and 1996, but later broken by critical vulnerabilities.

* TLS (Transport Layer Security): Created by the IETF starting in 1999 as the official

* TLS1.0& 1.1:Released in 1999 and 2006 (now deprecated).

* TLS 1.2 & 1.3: The only secure, active standards used on the web today.

TLS or SSL Certificate:

* Digital certificates (technically called X.509 Certificates) do not care about protocol versions.

* A certificate contains a public key and identity info.

* It works identically whether the server uses TLS 1.2, TLS 1.3, or legacy SSL.

* The term "SSL Certificate" persists purely because of 30 years of marketing and consumer familiarity.
Modern security tools and web browsers actually run on TLS.

What Actually Changed Under the Hood?

Handshake & Performance

= SSL Handshake: Required multiple back-and-forth round trips (2-RTT). Connection setup
was slow, creating noticeable lag for users.

= TLS Handshake: Streamlined the negotiation. TLS 1.3 cuts handshake latency in half by
allowing key exchange parameters to be sent in the very first message (1-RTT).

Security & Cryptography

= Weak Cryptography Excised: SSL allowed insecure encryption algorithms like RC4 stream
ciphers, RSA key transport, and MD5 hashing, which hackers easily broke. TLS removed
all of these in favor of authenticated encryption (AEAD) like AES-GCM and ChaCha20.

= Mandatory Forward Secrecy: Under SSL, if an attacker recorded encrypted web traffic

and stole the server's private key 5 years later, they could retroactively decrypt all that
past data. Modern TLS forces the use of temporary session keys (Ephemeral Diffie-
Hellman) so stolen server keys can't decrypt past recordings.

Note: Cryptographic algorithms will be dealt in courses like Applied Cryptography in detail.
COMPUTER NETWORKS %% PES
How Authentication Works

= Certificate Presentation: The server sends its digital certificate containing its Public Key
and the signature from a Certificate Authority (CA).

= CA Trust Verification: The browser checks the digital signature against its built-in
database of trusted Root Certificate Authorities (CAs) (like DigiCert or Let's Encrypt).

= Proof of Ownership (CertificateVerify): To prove the server isn't an attacker using a
stolen public certificate, the server encrypts/signs a unique handshake message using its
secret Private Key.

= Public Key Verification: The browser decrypts that signature using the Public Key from
the certificate. If the message decrypts successfully, it proves the server holds the
matching private key, confirming its identity.

TLS 1'3 UNIVERSITY

TLS 1.3 optimizes the process by combining key negotiation into the very first
packet.

= Step 1 (ClientHello + Key Share): The browser sends supported ciphers AND
proactively generates its ephemeral key parameters (Key Share), sending them in
the first packet.

= Step 2 (ServerHello & Encrypted Certificate): The server picks a cipher, generates
its matching key share, and calculates the symmetric session key. All subsequent
handshake messages—including the Server Certificate—are encrypted!

= Step 3 (Data Transmission): The client verifies the certificate signature and
derives the same symmetric key. Real HTTPS data flows immediately.

For returning visitors, TLS 1.3 introduces 0-RTT (Zero Round-Trip Time) mode:
= Uses a Pre-Shared Key (PSK) saved from the previous connection.

= The browser can send encrypted HTTP requests (like GET /home) in the very first
packet, eliminating latency entirely.
