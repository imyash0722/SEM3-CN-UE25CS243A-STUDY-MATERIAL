the destination port, while TCP needs the full 4-tuple?

UDP has no notion of an ongoing "connection" to distinguish; every datagram is
independent. TCP tracks per-connection state, so it needs the full tuple to know
which connection's state a segment belongs to

Questions @

1. Why does TCP need a connection "setup" step before any data flows, while UDP just sends?

« TCP has to establish shared state between sender and receiver first (for reliability, ordering,
flow/congestion control to work) — UDP has no such state to set up, which is exactly why it's
called a "no-frills" extension of IP. (Slide 10)
2. Name two things neither TCP nor UDP guarantees, no matter which one you pick.

» Delay guarantees and bandwidth guarantees

w

A segment header's first 32 bits hold two fields. What are they, and how wide is each?

« Source port # and destination port #, 16 bits each

4. If two different applications on your laptop both tried to bind to port 5775 at the same time,
what would happen?

« The second bind attempt would fail — a given port number can only be owned by one socket
on a host at a time

b

Why is a DNS query typically sent over UDP rather than TCP?

+ It's a small, one-shot request/response — the overhead of a TCP connection setup isn't worth
it for a single quick exchange, so UDP's speed wins out

Questions @

1. What would break if TCP demultiplexed using only the destination port, the same way
UDP does?

+ Every client connecting to the same server on the same port (e.g. port 80) would collide
into a single socket, since destination port alone can't tell two different clients apart —
this is exactly why TCP needs the full 4-tuple instead.

2. Inthe connection-oriented example, two segments came from the same source IP (C) but
different source ports, and still landed on different sockets. What does that prove about
how TCP demultiplexes?

« It proves TCP looks at the entire 4-tuple, not just the IP address — a single client machine
can have multiple independent connections to the same server, each tracked as its own
socket.

3.  Your laptop opens two browser tabs to the same website at the same time. Do they use
the same source port or different ones?

« Different ephemeral source ports — each new outgoing connection gets its own randomly
assigned port above 1023, which is also why the 4-tuple stays unique even though the
destination IP and port are identical for both tabs.

Questions @

1. Name the four fields of the UDP header, in order.
« Source port #, destination port #, length, checksum.

2.  How many bytes is a UDP header, and how does that compare with TCP?
+ 8 bytes (four 16-bit fields), versus a minimum of 20 for TCP.

3. The header is always exactly 8 bytes. So why is a length field needed?
« The payload is variable-length, and UDP keeps no connection state anywhere — each
datagram must be entirely self-describing about where its data ends.
4. What does the length field actually count?
« The whole UDP segment in bytes, header included — not just the payload.
5.  Why transmit the complement rather than the sum itself?

« So the receiver can add up everything including the checksum and simply test for all ones,
instead of recomputing and comparing.
