DNSSEC – Why It Matters
• Plain DNS has no authentication — a response claiming to be from an authoritative
server could be forged (cache poisoning / spoofing)
• DNSSEC adds digital signatures (RRSIG records) to DNS responses, so a resolver can
verify a record actually came from the zone's authoritative server
• Trust is chained: Root → TLD → Authoritative — each level signs the key of the level
below it
• It provides authentication and integrity, not confidentiality — DNS queries are still
visible in plaintext

Caching and Updating DNS Records
Suppose that a host apricot.nyu.edu queries dns.nyu.edu for the IP address for the
hostname cnn.com. After an hour later, another NYU host, say, kiwi.nyu.edu, also
queries dns.nyu.edu.
once (any) name server learns mapping, it caches mapping and immediately
returns a cached mapping in response to a query
• Caching improves response time
• cache entries timeout (disappear) after some time (TTL)
• TLD servers typically cached in local name servers
• thus root name servers not often visited

If cnn.com changes its IP address right now, how would you find out that some
corner of the internet is still resolving it to the old IP?
cached entries may be out-of-date (best-effort name-to-address translation!)
• if name host changes IP address, may not be known Internet-wide until all TTLs expire!

update/notify mechanisms proposed IETF standard
• RFC 2136

Questions
1. Why can't we just use IP addresses everywhere and skip names entirely?
Names are human-memorable and stable even when the underlying IP changes; DNS exists specifically to
bridge "what humans use" and "what routers use."
2. Why isn't DNS just one giant centralized server?
It wouldn't scale — single point of failure, unmanageable traffic volume (Comcast alone: 600B queries/day),
distant/slow lookups, and impossible maintenance.
3. Put these in order: TLD server, Authoritative server, Root server.
Root → TLD → Authoritative. Root points to the right TLD, TLD points to the right organization's authoritative
server, authoritative server has the actual answer.
4. What's the difference between a domain and a zone?
A domain is the naming subtree (e.g. everything under example.com); a zone is an administrative boundary —
who actually manages and maintains the records for a piece of that tree. One domain can be split into many
independently-managed zones.
5. Give a practical reason an organization would split its domain into multiple zones.
To delegate control — e.g. a CSE department managing its own cse.pes.edu records without needing central IT
to make every change, and so a mistake in one zone doesn't take down the others.

COMPUTER NETWORKS
Questions
6. In an iterated query, what does a server say when it doesn't know the answer?
"I don't know this name, but ask this server" — it gives a referral and hands the querying party the
responsibility. (Slide 11)
7. In a recursive query, who does the extra work of following referrals?
The server that was contacted does it on the client's behalf, rather than sending the client elsewhere.
(Slide 12)
8. Which DNS flag in a response tells you whether a server is willing to do recursive resolution for you?
The RA (Recursion Available) flag. Root and TLD servers never set it — by design, they only operate
iteratively.
9. What does a TTL control, and what happens right after it hits zero?
How long a resolver may keep serving a cached answer without re-checking. Once it expires, the entry is
discarded and the resolver must re-query — walking the hierarchy fresh if needed. (Slide 13)
10. A company changes a server's IP address. Why might some users still reach the old IP for hours
afterward?
DNS caching is best-effort — any resolver that already cached the old record keeps serving it until its TTL
expires; there's no way to force-flush every cache on the internet at once. (Slide 13)

COMPUTER NETWORKS
Questions
11. What's the standard operational fix for minimizing disruption during a planned IP change?
Lower the TTL well in advance, wait for the old (long) TTL to fully drain everywhere, make the change, then
raise the TTL back — bounding the worst-case staleness window instead of eliminating it.
12. Name the four DNS record types and what each maps.
A: hostname → IPv4 address. NS: domain → authoritative name server. CNAME: alias name → canonical name.
MX: domain → mail server.
13. What's the difference between host aliasing (CNAME) and mail server aliasing (MX)?
CNAME points one hostname at another hostname (e.g. www.ibm.com → servereast.backup2.ibm.com); MX
specifically tells you where a domain's email should be delivered, and — unlike CNAME — supports
priority/fallback servers.
14. What kind of DNS record has no fixed structure, and what are two real uses for it?
TXT — arbitrary free text. Used for domain ownership verification (e.g. google-site-verification=...) and email
anti-spoofing policies like SPF/DKIM.
15. What problem does DNSSEC solve that TTL/caching does not?
Authenticity and integrity — DNSSEC lets a resolver verify a response actually came from the real authoritative
server (via signed records, chained root → TLD → authoritative), preventing forged/poisoned answers. It says
nothing about staleness of a legitimately-changed record — that's still governed by TTL.
