ECN: signalling congestion without dropping packets %

Router is congested. Instead of dropping the packet, it sets the CE bit (Congestion Experienced) — two bits in the IP
header's ToS field. The packet is still delivered.

Receiver sees CE. It sets the ECE flag (ECN-Echo) in the TCP header of its very next ACK.

Sender sees ECE. It halves cwnd exactly as if it had detected loss, and sets CWR (Congestion Window Reduced) to confirm it
acted.

Router, sender and receiver must all support ECN — which is why a mechanism specified in 1999 took two decades to see
real deployment.

Congestion signalled, zero packets destroyed. But the feedback still costs a full round trip, and the network itself had to be
modified to send it. That deployment cost is exactly why TCP chose end-to-end inference instead.

Why QUIC uses UDP?

UNIVERSITY

Since TCP is hardcoded into operating system kernels and worldwide network
middleboxes (like routers and firewalls), upgrading it globally is nearly impossible.

By building on top of UDP—which is universally accepted by all network hardware—
QUIC implements its advanced reliability, congestion control, and packet recovery
directly in user space (application layer) without requiring OS kernel updates.

Using UDP also makes QUIC easier to deploy without changing the underlying IP
stack.

QUIC implements its own: Reliability, Acknowledgments, Retransmission, Congestion
control, Flow control, Connection management, Stream multiplexing, Security

Why HTTP/2 could not fix this on its own

HTTP/2 already multiplexed many requests over one connection — but it did so above TCP, and TCP delivers a single ordered byte stream.
One lost segment makes TCP withhold every later byte, including bytes belonging to completely unrelated HTTP/2 streams. The multiplexing
was real; the transport underneath knew nothing about it. You cannot fix this from above TCP, which is precisely why QUIC had to replace
the transport rather than sit on top of it.

Example: Suppose the 0-RTT data is an HTTP request:

GET /product/42 — fetching a product page. If an attacker replays this 10 times, the server just serves the same page 10 times.
Annoying at worst, harmless.

POST /orders {item: 42, qty: 1} — placing an order. If an attacker replays this, the server may create the order 10 times — 10
charges, 10 shipments.

QUIC/TLS 1.3 specs put the responsibility on the application, not the protocol: only send data in the O-RTT flight if it's safe to have
processed more than once. A browser or server implementation typically restricts what's allowed to go in that first flight for exactly
this reason.

Why fragmentation is avoided

= One lost fragment loses them all
IP never resends. If one fragment is missing, the destination throws away the rest.

= TCP sizes its segments to fit
1,500 - 20 (IP) - 20 (TCP) = 1,460 bytes of data, so IP never needs to split.

= Senders ask routers not to split
The DF bit is set. A router that can't forward the packet drops it and replies with the MTU it needs.

= IPV6 routers never fragment
Only the sender may split an IPv6 packet. Routers just drop it and report back.

Result: the sender learns the smallest MTU on the whole path and never sends anything bigger. This is called path
MTU discovery, and it is why routers today almost never fragment.

Step 1: Determine the requirements
* Identify the number of subnets required.
* Determine the number of hosts needed per subnet.

Step 2: Determine the subnet and host bits
¢ Use the 2" - 2 formula to determine the number of subnet bits and host bits required.
* If multiple subnet masks satisfy the requirements, choose the one that provides better
future scalability.
If more subnets are likely to be added -> allocate more subnet bits.
If more hosts are likely to be added to existing subnets - allocate more host bits.
* Avoid using all available subnets or host addresses immediately. Leave room for future
growth.

Key Characteristics of SDN ‘%

PES

UNIVERSITY

1: Generalized “flow-based” forwarding (e.g., OpenFlow) —

Packet forwarding by SDN-controlled switches can be based on any number of header field values
in the transport-layer, network-layer, or link-layer header. OpenFlow abstraction allows forwarding
based on eleven different header field values. This contrasts sharply with the traditional approach
to router-based forwarding where forwarding of IP datagrams was based solely on a datagram’s
destination IP address. Here, packet forwarding rules are specified in a switch’s flow table; and it is
the job of the SDN control plane to compute, manage and install flow table entries in all of the
network’s switches.

2: Control and Data plane separation —

The data plane consists of the network’s switches—relatively simple (but fast) devices that execute
the “match plus action” rules in their flow tables. The control plane consists of servers and software
that determine and manage the switches’ flow tables.
COMPUTER NETWORKS

e PES
Key Characteristics of SDN

UNIVERSITY

3. Network control plane functions: external to data-plane switches —

SDN control plane is implemented in software. Unlike traditional routers, however, this software executes on
servers that are both distinct and remote from the network’s switches. As shown in Figure, the control plane
itself consists of two components—an SDN controller (or network operating system [Gude 2008]) and a set of
network-control applications. The controller maintains accurate network state information (e.g., the state of
remote links, switches, and hosts); provides this information to the network-control applications running in
the control plane; and provides the means through which these applications can monitor, program, and
control the underlying network devices. Although the controller in Figure is shown as a single central server,
in practice the controller is only logically centralized; it is typically implemented on several servers that
provide coordinated, scalable performance and high availability.

4. Programmable control applications —

The network is programmable through the network-control applications running in the control plane. These
applications represent the “brains” of the SDN control plane, using the APIs provided by the SDN controller to
specify and control the data plane in the network devices.

For example, a routing network-control application might determine the end-end paths between sources and
destinations. Yet another application might have switches forward packets in a manner that performs server
load balancing

Components of SDN ‘%

UNIVERSITY

A communication layer: Communicating between the SDN controller and controlled
network devices. Clearly, if an SDN controller is going to control the operation of a remote
SDN-enabled switch, host, or other device, a protocol is needed to transfer information
between the controller and that device. In addition, a device must be able to communicate
locally-observed events to the controller (for example, a message indicating that an
attached link has gone up or down, that a device has just joined the network, or a heartbeat
indicating that a device is up and operational). These events provide the SDN controller with
an up-to-date view of the network’s state. This protocol constitutes the lowest layer of the
controller architecture, as shown in Figure. The communication between the controller and
the controlled devices cross what has come to be known as the controller’s “southbound”
interface. OpenFlow is implemented in most, if not all, SDN controllers.
COMPUTER NETWORKS

A2\ PES
Components of SDN ‘%

UNIVERSITY

A network-wide state-management layer: The ultimate control decisions made by the SDN control
plane—for example, configuring flow tables in all switches to achieve the desired end-end
forwarding, to implement load balancing, or to implement a particular firewalling capability—will
require that the controller have up-to-date information about state of the networks’ hosts, links,
switches, and other SDN-controlled devices. A switch’s flow table contains counters whose values
might also be profitably used by network-control applications; these values should thus be available
to the applications. Since the ultimate aim of the control plane is to determine flow tables for the
various controlled devices, a controller might also maintain a copy of these tables.

The interface to the network-control application layer: The controller interacts with network-
control applications through its “northbound” interface. This API allows network-control applications
to read/write network state and flow tables within the state-management layer. Applications can
register to be notified when state-change events occur, so that they can take actions in response to
network event notifications sent from SDN-controlled devices.

Workflow of P4 Program

= Each section of the P4 program is linked to a different block that performs a specific
function.

= The P4 program is divided into four major sections: data declaration, parser logic, a match-

Congestion Window Size Changes Over Time:

1. Slow Start: The congestion window begins at 1 MSS. For each incoming acknowledgment, cwnd
increases by 1 MSS, effectively doubling the congestion window every round trip time in an exponential

progression.
2. Transition to Congestion Avoidance: Once cwnd reaches the slow start threshold (ssthresh), the
algorithm shifts to Congestion Avoidance.

3. Congestion Avoidance: In this state, cwnd increases linearly by approximately 1 MSS per round trip time
to probe for bandwidth cautiously until another packet loss event is encountered.
