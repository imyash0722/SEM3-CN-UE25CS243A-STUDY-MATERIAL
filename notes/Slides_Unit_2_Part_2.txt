Summary
Multiplexing, demultiplexing: based on segment, datagram header field values
UDP: demultiplexing using destination port number (only)
TCP: demultiplexing using 4-tuple: source and destination IP addresses, and port
numbers
Multiplexing/demultiplexing happen at all layers
Given everything we just covered — why does UDP get away with just checking
the destination port, while TCP needs the full 4-tuple?
UDP has no notion of an ongoing "connection" to distinguish; every datagram is
independent. TCP tracks per-connection state, so it needs the full tuple to know
which connection's state a segment belongs to

Questions
1.

Why does TCP need a connection "setup" step before any data flows, while UDP just sends?
• TCP has to establish shared state between sender and receiver first (for reliability, ordering,
flow/congestion control to work) — UDP has no such state to set up, which is exactly why it's
called a "no-frills" extension of IP. (Slide 10)

2.

Name two things neither TCP nor UDP guarantees, no matter which one you pick.
• Delay guarantees and bandwidth guarantees

3.

A segment header's first 32 bits hold two fields. What are they, and how wide is each?
• Source port # and destination port #, 16 bits each

4.

If two different applications on your laptop both tried to bind to port 5775 at the same time,
what would happen?
• The second bind attempt would fail — a given port number can only be owned by one socket
on a host at a time

5.

Why is a DNS query typically sent over UDP rather than TCP?
• It's a small, one-shot request/response — the overhead of a TCP connection setup isn't worth
it for a single quick exchange, so UDP's speed wins out

COMPUTER NETWORKS
Questions
1.

What would break if TCP demultiplexed using only the destination port, the same way
UDP does?
• Every client connecting to the same server on the same port (e.g. port 80) would collide
into a single socket, since destination port alone can't tell two different clients apart —
this is exactly why TCP needs the full 4-tuple instead.

2.

In the connection-oriented example, two segments came from the same source IP (C) but
different source ports, and still landed on different sockets. What does that prove about
how TCP demultiplexes?
• It proves TCP looks at the entire 4-tuple, not just the IP address — a single client machine
can have multiple independent connections to the same server, each tracked as its own
socket.

3.

Your laptop opens two browser tabs to the same website at the same time. Do they use
the same source port or different ones?
• Different ephemeral source ports — each new outgoing connection gets its own randomly
assigned port above 1023, which is also why the 4-tuple stays unique even though the
destination IP and port are identical for both tabs.

Questions
1.

Name the four fields of the UDP header, in order.
• Source port #, destination port #, length, checksum.

2.

How many bytes is a UDP header, and how does that compare with TCP?
• 8 bytes (four 16-bit fields), versus a minimum of 20 for TCP.

3.

The header is always exactly 8 bytes. So why is a length field needed?
• The payload is variable-length, and UDP keeps no connection state anywhere — each
datagram must be entirely self-describing about where its data ends.

4.

What does the length field actually count?
• The whole UDP segment in bytes, header included — not just the payload.

5.

Why transmit the complement rather than the sum itself?
• So the receiver can add up everything including the checksum and simply test for all ones,
instead of recomputing and comparing.

COMPUTER NETWORKS
Computing UDP Checksum – 5 Steps

1

Split the segment into 16-bit words

Header fields and data, all treated as plain 16-bit integers

2

Add the words together

Ordinary binary addition, one word at a time

3

Handle the wraparound carry

Any carry out of the most significant bit is added back into the low end
— this is the step everyone forgets

4

That result is the SUM

Keep going until every word has been added in

5

Flip every bit — that is the CHECKSUM One's complement of the sum; this is what goes in the header field

What the Checksum Catches – What it Misses
ALWAYS CAUGHT

•

Any single bit flip, anywhere in the segment

•

ANY pattern of 1 to 15 bit flips confined to a single 16bit word

•

Any burst error shorter than 16 bits

•

Most multi-word errors — they only cancel in very
specific offsetting patterns

CAN SLIP THROUGH

•

Two bits flipping in OPPOSITE directions in DIFFERENT
words — the errors cancel in the sum (the deck's
“weak protection” example)

•

Any set of errors across words whose net effect on
the sum is zero

•

One degenerate case: flipping all 16 bits of a word
that was all-zeros or all-ones

The checksum is STRONG within a word and WEAK across words. Errors
confined to one 16-bit word are essentially always caught — the vulnerability
needs errors spread over two or more words in offsetting directions.

rdt3.0: pipelined protocol operations
The solution to the performance problem is a simple one: rather than operate in a stop-and-wait manner,
the sender is allowed to send multiple packets without waiting for acknowledgements
Since the many in-transit sender-to-receiver packets can be visualized as filling a pipeline, this technique is
known as pipelining.
pipelining: sender allows multiple, “in-flight”, yet-to-be-acknowledged packets
• range of sequence numbers must be increased (must have a unique sequence number and there may
be multiple, in-transit, unacknowledged packets).
• buffering at sender and/or receiver

Why not just set the timeout to the measured RTT?
→ RTT varies constantly; too short causes needless retransmissions that add load
to an already-struggling network, too long wastes time. The 4×DevRTT margin is
a safety cushion that widens automatically when the network gets erratic.
Why 4 times the deviation rather than 1 or 2?
→ it's an engineering constant, tuned empirically for a conservative margin.
