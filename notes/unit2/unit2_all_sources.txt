DNSSEC — Why It Matters @@

UNIVERSITY

Plain DNS has no authentication — a response claiming to be from an authoritative
server could be forged (cache poisoning / spoofing)

DNSSEC adds digital signatures (RRSIG records) to DNS responses, so a resolver can
verify a record actually came from the zone's authoritative server

Trust is chained: Root = TLD - Authoritative — each level signs the key of the level
below it

It provides authentication and integrity, not confidentiality — DNS queries are still
visible in plaintext

Caching and Updating DNS Records @

Suppose that a host apricot.nyu.edu queries dns.nyu.edu for the IP address for the

hostname cnn.com. After an hour later, another NYU host, say, kiwi.nyu.edu, also
gueries dns.nyu.edu.

once (any) name server learns mapping, it caches mapping and immediately
returns a cached mapping in response to a query

* Caching improves response time

* cache entries timeout (disappear) after some time (TTL)

* TLD servers typically cached in local name servers
¢ thus root name servers not often visited

If cnn.com changes its IP address right now, how would you find out that some
corner of the internet is still resolving it to the old IP?

cached entries may be out-of-date (best-effort name-to-address translation!)
* if name host changes IP address, may not be known Internet-wide until all TTLs expire!

Questions

UNIVERSITY

1. Why can't we just use IP addresses everywhere and skip names entirely?

Names are human-memorable and stable even when the underlying IP changes; DNS exists specifically to
bridge "what humans use" and "what routers use."

2. Why isn't DNS just one giant centralized server?

It wouldn't scale — single point of failure, unmanageable traffic volume (Comcast alone: 600B queries/day),
distant/slow lookups, and impossible maintenance.

3. Put these in order: TLD server, Authoritative server, Root server.

Root = TLD - Authoritative. Root points to the right TLD, TLD points to the right organization's authoritative
server, authoritative server has the actual answer.

4. What's the difference between a domain and a zone?

A domain is the naming subtree (e.g. everything under example.com); a zone is an administrative boundary —
who actually manages and maintains the records for a piece of that tree. One domain can be split into many
independently-managed zones.

5. Give a practical reason an organization would split its domain into multiple zones.

To delegate control — e.g. a CSE department managing its own cse.pes.edu records without needing central IT
to make every change, and so a mistake in one zone doesn't take down the others.

Questions @

6. In an iterated query, what does a server say when it doesn't know the answer?

"I don't know this name, but ask this server" — it gives a referral and hands the querying party the
responsibility. (Slide 11)

7. In a recursive query, who does the extra work of following referrals?

The server that was contacted does it on the client's behalf, rather than sending the client elsewhere.
(Slide 12)

8. Which DNS flag in a response tells you whether a server is willing to do recursive resolution for you?
The RA (Recursion Available) flag. Root and TLD servers never set it — by design, they only operate
iteratively.

9. What does a TTL control, and what happens right after it hits zero?

How long a resolver may keep serving a cached answer without re-checking. Once it expires, the entry is
discarded and the resolver must re-query — walking the hierarchy fresh if needed. (Slide 13)

10. A company changes a server's IP address. Why might some users still reach the old IP for hours
afterward?

DNS caching is best-effort — any resolver that already cached the old record keeps serving it until its TTL
expires; there's no way to force-flush every cache on the internet at once. (Slide 13)

Questions @

11. What's the standard operational fix for minimizing disruption during a planned IP change?

Lower the TTL well in advance, wait for the old (long) TTL to fully drain everywhere, make the change, then
raise the TTL back — bounding the worst-case staleness window instead of eliminating it.

12. Name the four DNS record types and what each maps.

A: hostname - IPv4 address. NS: domain - authoritative name server. CNAME: alias name —» canonical name.
MX: domain - mail server.

13. What's the difference between host aliasing (CNAME) and mail server aliasing (MX)?

CNAME points one hostname at another hostname (e.g. www.ibm.com - servereast.backup2.ibm.com); MX
specifically tells you where a domain's email should be delivered, and — unlike CNAME — supports
priority/fallback servers.

14. What kind of DNS record has no fixed structure, and what are two real uses for it?

TXT — arbitrary free text. Used for domain ownership verification (e.g. google-site-verification=...) and email
anti-spoofing policies like SPF/DKIM.

15. What problem does DNSSEC solve that TTL/caching does not?

Authenticity and integrity — DNSSEC lets a resolver verify a response actually came from the real authoritative
server (via signed records, chained root - TLD - authoritative), preventing forged/poisoned answers. It says
nothing about staleness of a legitimately-changed record — that's still governed by TTL.

Given everything we just covered — why does UDP get away with just checking
the destination port, while TCP needs the full 4-tuple?

UDP has no notion of an ongoing "connection" to distinguish; every datagram is
independent. TCP tracks per-connection state, so it needs the full tuple to know
which connection's state a segment belongs to

Questions @

1. Why does TCP need a connection "setup" step before any data flows, while UDP just sends?

« TCP has to establish shared state between sender and receiver first (for reliability, ordering,
flow/congestion control to work) — UDP has no such state to set up, which is exactly why it's
called a "no-frills" extension of IP. (Slide 10)
2. Name two things neither TCP nor UDP guarantees, no matter which one you pick.

» Delay guarantees and bandwidth guarantees

w

A segment header's first 32 bits hold two fields. What are they, and how wide is each?

« Source port # and destination port #, 16 bits each

4. If two different applications on your laptop both tried to bind to port 5775 at the same time,
what would happen?

« The second bind attempt would fail — a given port number can only be owned by one socket
on a host at a time

b

Why is a DNS query typically sent over UDP rather than TCP?

+ It's a small, one-shot request/response — the overhead of a TCP connection setup isn't worth
it for a single quick exchange, so UDP's speed wins out

Questions @

1. What would break if TCP demultiplexed using only the destination port, the same way
UDP does?

+ Every client connecting to the same server on the same port (e.g. port 80) would collide
into a single socket, since destination port alone can't tell two different clients apart —
this is exactly why TCP needs the full 4-tuple instead.

2. Inthe connection-oriented example, two segments came from the same source IP (C) but
different source ports, and still landed on different sockets. What does that prove about
how TCP demultiplexes?

« It proves TCP looks at the entire 4-tuple, not just the IP address — a single client machine
can have multiple independent connections to the same server, each tracked as its own
socket.

3.  Your laptop opens two browser tabs to the same website at the same time. Do they use
the same source port or different ones?

« Different ephemeral source ports — each new outgoing connection gets its own randomly
assigned port above 1023, which is also why the 4-tuple stays unique even though the
destination IP and port are identical for both tabs.

Questions @

1. Name the four fields of the UDP header, in order.
« Source port #, destination port #, length, checksum.

2.  How many bytes is a UDP header, and how does that compare with TCP?
+ 8 bytes (four 16-bit fields), versus a minimum of 20 for TCP.

3. The header is always exactly 8 bytes. So why is a length field needed?
« The payload is variable-length, and UDP keeps no connection state anywhere — each
datagram must be entirely self-describing about where its data ends.
4. What does the length field actually count?
« The whole UDP segment in bytes, header included — not just the payload.
5.  Why transmit the complement rather than the sum itself?

« So the receiver can add up everything including the checksum and simply test for all ones,
instead of recomputing and comparing.

Report Questions:
How does UDP differ from TCP?

« Connectionless vs Connection-Oriented: UDP does not establish a connection before sending data;
TCP requires a 3-way handshake (SYN, SYN-ACK, ACK).

« Delivery Guarantees: UDP does not guarantee delivery, order, or retransmission of lost packets; TCP
provides guaranteed in-order delivery and automatic retransmission.

« Header Size: UDP has a fixed, lightweight 8-byte header; TCP's header is at least 20 bytes (and up to
60 bytes with options).

« Connection Teardown: UDP simply transmits datagrams; TCP requires FIN/ACK teardown packets to
cleanly close a connection.

Why is UDP suitable for DNS?

« Fits Single Packet: Standard DNS queries and replies are small enough to fit within a single
packet/datagram, requiring no packet fragmentation or reassembly.

« Low Latency: Eliminating the 3-way handshake significantly reduces latency for routine, frequent
domain lookups.

« Simple Client-Side Retransmission: If a query or response packet is dropped, the client resolver
simply retransmits the query after a brief timeout.

« Fallback Design: TCP is reserved strictly as a fallback when response payloads exceed standard size
limits (indicated by the TC flag).

Observations about UDP traffic in Wireshark:

« Independent Datagrams: Each message was transmitted as an independent datagram with no
sequence numbers or acknowledgment numbers.

« Minimal Overhead: Packets consist strictly of the 8-byte UDP header plus the payload length.

« Error Handling: When sending to a port with no listening server, the operating system returns an
ICMP 'Port Unreachable’ error, showing UDP has no built-in application session handling.

« Port Behavior: The client used a high ephemeral source port, while the destination port was fixed at
54321.
PART 3: Analysis of the UDP Protocol in DNS using Wireshark [4M]

1. First UDP Segment in Trace

A. Packet number: 5363 (from the DNS trace to 1.1.1.1)

B. Application-layer payload message: DNS (Domain Name System) — Standard query, A record for
www.google.com (Transaction ID: Oxcade).

C. UDP header fields: 4 fields total (each 16 bits / 2 bytes):

1. Source Port: 16 bits (2 bytes) — High ephemeral port dynamically assigned to the client (Value:
40136).

2. Destination Port: 16 bits (2 bytes) — Standard well-known port for DNS service (Value: 53).

3. Length: 16 bits (2 bytes) — Total length of UDP header plus application payload in bytes (Value: 63
bytes).

4. Checksum: 16 bits (2 bytes) — Checksum used for end-to-end packet integrity verification.

2. UDP Header Length

The length of the UDP header is exactly 8 bytes (fixed size across all UDP datagrams: 2 bytes each for
Source Port, Destination Port, Length, and Checksum).

3. Query and Response UDP Packet Pair

A. Packet numbers: Packet 5363 (DNS Query) and Packet 5420 (DNS Response)
B. Source Port (Packet 5363 - Query): 40136

C. Destination Port (Packet 5363 - Query): 53

D. Source Port (Packet 5420 - Response): 53

E. Destination Port (Packet 5420 - Response): 40136

Relationship between Port Numbers:

The port numbers are reversed (swapped) between the query and response packets:

Query (Client — Server): The client host initiates the query using a dynamic/ephemeral high-
numbered port (40136) as the Source Port, sending it to the server's well-known DNS port 53 as the
Destination Port.

Response (Server - Client): The DNS server responds from its port 53 (now the Source Port)
directed back to the client's ephemeral port 40136 (now the Destination Port).

Purpose & Mechanism: This port swapping allows the client operating system's transport layer to
demultiplex and route the incoming DNS response directly to the specific socket and process that issued
the request.

How does UDP differ from TCP?

« Connectionless vs Connection-Oriented: UDP does not establish a connection before sending data;
TCP requires a 3-way handshake (SYN, SYN-ACK, ACK).

« Delivery Guarantees: UDP does not guarantee delivery, order, or retransmission of lost packets; TCP
provides guaranteed in-order delivery and automatic retransmission.

« Header Size: UDP has a fixed, lightweight 8-byte header; TCP's header is at least 20 bytes (and up to
60 bytes with options).

« Connection Teardown: UDP simply transmits datagrams; TCP requires FIN/ACK teardown packets to
cleanly close a connection.

Why is UDP suitable for DNS?

« Fits Single Packet: Standard DNS queries and replies are small enough to fit within a single
packet/datagram, requiring no packet fragmentation or reassembly.

« Low Latency: Eliminating the 3-way handshake significantly reduces latency for routine, frequent
domain lookups.

« Simple Client-Side Retransmission: If a query or response packet is dropped, the client resolver
simply retransmits the query after a brief timeout.

« Fallback Design: TCP is reserved strictly as a fallback when response payloads exceed standard size
limits (indicated by the TC flag).

Observations about UDP traffic in Wireshark:

« Independent Datagrams: Each message was transmitted as an independent datagram with no
sequence numbers or acknowledgment numbers.

« Minimal Overhead: Packets consist strictly of the 8-byte UDP header plus the payload length.

« Error Handling: When sending to a port with no listening server, the operating system returns an
ICMP 'Port Unreachable’ error, showing UDP has no built-in application session handling.

« Port Behavior: The client used a high ephemeral source port, while the destination port was fixed at
54321.
PART 3: Analysis of the UDP Protocol in DNS using Wireshark [4M]

1. First UDP Segment in Trace

A. Packet number: 5363 (from the DNS trace to 1.1.1.1)

B. Application-layer payload message: DNS (Domain Name System) — Standard query, A record for
www.google.com (Transaction ID: Oxcade).

C. UDP header fields: 4 fields total (each 16 bits / 2 bytes):

1. Source Port: 16 bits (2 bytes) — High ephemeral port dynamically assigned to the client (Value:
40136).

2. Destination Port: 16 bits (2 bytes) — Standard well-known port for DNS service (Value: 53).

3. Length: 16 bits (2 bytes) — Total length of UDP header plus application payload in bytes (Value: 63
bytes).

4. Checksum: 16 bits (2 bytes) — Checksum used for end-to-end packet integrity verification.

2. UDP Header Length

The length of the UDP header is exactly 8 bytes (fixed size across all UDP datagrams: 2 bytes each for
Source Port, Destination Port, Length, and Checksum).

3. Query and Response UDP Packet Pair

A. Packet numbers: Packet 5363 (DNS Query) and Packet 5420 (DNS Response)
B. Source Port (Packet 5363 - Query): 40136

C. Destination Port (Packet 5363 - Query): 53

D. Source Port (Packet 5420 - Response): 53

E. Destination Port (Packet 5420 - Response): 40136

Relationship between Port Numbers:

The port numbers are reversed (swapped) between the query and response packets:

Query (Client — Server): The client host initiates the query using a dynamic/ephemeral high-
numbered port (40136) as the Source Port, sending it to the server's well-known DNS port 53 as the
Destination Port.

Response (Server - Client): The DNS server responds from its port 53 (now the Source Port)
directed back to the client's ephemeral port 40136 (now the Destination Port).

Purpose & Mechanism: This port swapping allows the client operating system's transport layer to
demultiplex and route the incoming DNS response directly to the specific socket and process that issued
the request.
